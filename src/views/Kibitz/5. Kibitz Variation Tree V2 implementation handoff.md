# Kibitz Variation Tree V2 implementation handoff

This handoff defines the Kibitz-specific variation-tree behavior after product discussion with OGS devs. It is meant for a fresh implementation, not an incremental patch on top of generic tree behavior.

It should fit the broader Kibitz product model already established elsewhere:

* variations belong to **Compare**, not the proposal surface
* Compare is the intentional inspection surface
* the backend already treats variations as room-scoped persisted objects
* mobile uses the same product logic, but with one board area at a time rather than two gobans side by side.   

## 1. Core decision

Kibitz does **not** use a plain generic move-tree model for posted variations.

Instead:

* posted variations are **immutable**
* multiple posted variations may be visible in the tree at once
* visibility is controlled by explicit **toggles**
* clicking recall should **leave other visible variations on** and only change selection/focus
* if the user is focused inside a variation when the live game advances, the viewport should **stay where the user is**
* starting from a posted variation creates a **new draft**, not an edit of the posted one

This is why a custom implementation is wanted.

## 2. Product behavior summary

The variation system has 3 layers:

### A. Base game layer

The room’s watched game.

* always exists
* always anchors the tree
* continues to receive new moves if the source game is live

### B. Posted variation layer

Persisted room variations.

* immutable
* toggleable visible/hidden
* recallable/focusable
* multiple may be shown at once if they belong to the same base game

### C. Draft variation layer

The local user’s unposted working branch.

* editable
* separate from posted history
* may begin from base game or from a posted variation position

## 3. Non-negotiable rules

### Posted variations are immutable

Once posted, the move content of that variation never changes.

### Posted variations are room artifacts

They are part of room history and should continue to fit the room-scoped variation model already assumed by the backend handoff. 

### A posted variation can be used as a starting point

But this creates a new draft. It does not mutate the posted branch.

### Multiple posted variations may be visible

But only through an explicit local toggle model.

### Recall does not clear the others

Recalling variation X:

* ensures X is visible
* selects/focuses X
* leaves other visible posted variations visible

### Live game updates do not steal focus

If the user is currently viewing a posted variation or draft and the live base game receives a new move, the tree data updates but the viewport stays where the user is.

### Cross-game merging is forbidden

Only variations that belong to the same base game may appear together in one composed tree. This matches the broader Kibitz rule that old-board variations remain accessible but must stay separated from the current game context. 

## 4. Mental model for the user

The user should experience 3 distinct states:

### State 1: viewing the room game

Tree shows base game only, or base game plus whichever posted variations they have toggled on.

### State 2: viewing posted history

User recalls one or more posted variations. They can inspect them, click through them, and compare them, but not edit them.

### State 3: authoring a new variation

User starts from the base game or a posted variation position and creates a new draft branch. This draft is editable until posted.

The UI must make it obvious which of these 3 states the user is in.

## 5. Tree composition model

The visible tree should be treated as a **composed projection**, not as one permanently mutated canonical tree.

Recommended conceptual inputs:

* `baseGameTree`
* `postedVariationsById`
* `visiblePostedVariationIds`
* `selectedPostedVariationId | null`
* `activeDraftVariation | null`

Recommended conceptual output:

* `composedTreeView`

Composition order:

1. start from base game tree
2. overlay all toggled-on posted variations for that same base game
3. overlay active draft, if any
4. apply styling/selection/focus state

Do not rely on “just keep merging branches forever as the user clicks stuff.” That was the confusing behavior you were trying to get away from.

## 6. Selection, visibility, and focus

These must be kept separate.

### Visibility

Whether a posted variation is currently shown in the tree.

### Selection

Which posted variation is currently the focused one.

### Focus / viewport position

Which move/node the user is currently looking at.

These are related but not identical.

### Required behavior

#### Recall action

When user clicks recall on variation X:

* if X is hidden, toggle it on
* set `selectedPostedVariationId = X`
* navigate/focus the tree to X’s relevant node or endpoint
* leave all other currently visible posted variations visible

#### Toggle on

When user toggles variation X on:

* it appears in the tree
* it receives visible branch identity
* it may remain unselected unless this toggle was initiated by recall/post flow

#### Toggle off

When user toggles variation X off:

* remove it from tree
* if X was selected, clear selected state or fall back to base-game selection
* do not leave selected state pointing to something invisible

## 7. Visual identity rules

Since multiple posted variations may coexist, branches need identity.

### Required

A visible posted variation must be visually linkable between:

* its entry in the variation list
* its branch in the tree

### Recommended V2 implementation

Use a color-linked model.

Each visible posted variation gets:

* a color chip or accent in the variation list
* the same accent on its tree branch
* a stronger selected style if it is the active selected posted variation

### Draft branch styling

Draft should not look like posted history.

Recommended:

* neutral grey or subdued accent
* dashed/softer emphasis acceptable
* clearly distinct from posted-variation colors

### Base game styling

Base branch should remain neutral and authoritative.

## 8. Variation list responsibilities

The variation list becomes the control surface for posted branches.

Each posted variation row should support:

* **recall**: show if needed + select + focus
* **toggle**: show/hide in tree
* visible indicator
* selected indicator
* optional color indicator

Recommended interaction split:

* clicking the row body/title = recall/select
* clicking the eye/toggle/icon = show/hide

That keeps the two behaviors distinct.

## 9. Editing rules

### Posted variation clicks are view-only

Clicking through nodes of a posted variation should navigate that variation but should not silently turn it editable.

### Entering edit mode must be deliberate

To start a new draft from a posted variation, the user should perform an explicit action or a clearly-defined play action that the UI interprets as “start new variation from here.”

### Starting a draft from a posted variation

When user starts playing from a posted variation position:

* create new local draft state
* anchor draft from the chosen node/position
* keep the posted variation intact
* do not overwrite or truncate posted history

## 10. Posting flow

When a draft is posted:

1. validate draft payload
2. persist it as a new room variation
3. emit/add `variation_posted` room event as already intended by the backend model 
4. clear or finalize draft editing state
5. automatically toggle the newly posted variation on for the posting user
6. select/focus the newly posted variation
7. assign it posted-variation visual identity

Other users should see the new variation appear in room history/list, but it does **not** need to auto-toggle on in their tree.

## 11. Live game update behavior

The base game branch may continue to grow while the user is inspecting posted variations.

Required behavior:

* apply new live moves to base tree data
* keep visible posted variations visible
* keep draft intact
* do not snap viewport away from the user’s current location
* do not clear selection just because live moves arrived

This specific point was explicitly settled: stay where the user is.

## 12. Compare-mode integration

This implementation should fit the broader Kibitz page rules:

* variations are a Compare-surface feature
* opening a variation should place the user into Compare context
* the variation board should occupy the comparison board surface on desktop
* the room board remains the anchor board
* closing variation viewing should return cleanly to Watch unless the user intentionally remains in Compare. 

The variation tree, controls, and actions should stay visually associated with the comparison board, not with proposals or unrelated room panels. 

## 13. Mobile integration

Mobile uses the same model, but only one board area at a time.

So on mobile:

* opening a variation should switch the board area into Compare state
* the variation occupies the main board area
* the lower panel shows variation context/controls
* closing Compare returns to the room board and previous panel
* there should never be an attempt to show the full room board and full variation board simultaneously on a normal phone. 

The tree model itself stays the same; only the spatial presentation changes.

## 14. Board-change interaction

If the room changes to a different watched game:

* replace the base game tree with the new game
* clear current composed-tree visibility state for the old game
* keep old variations accessible in history under prior-game context
* do not merge prior-game variations into the new current-game tree

This should align with the existing Kibitz rule that old-board variations remain accessible but visually separated. 

## 15. Suggested state model

A practical frontend state shape could look like this:

```ts
type PostedVariationId = string;

interface VariationTreeState {
  baseGameId: number;
  visiblePostedVariationIds: PostedVariationId[];
  selectedPostedVariationId: PostedVariationId | null;
  activeDraftVariation: DraftVariation | null;
  focusedNodePath: string | null;
}
```

Supporting derived selectors:

```ts
getVisiblePostedVariationsForBaseGame(state, baseGameId)
getSelectedPostedVariation(state)
getComposedTreeView(state)
isPostedVariationVisible(state, id)
isPostedVariationSelected(state, id)
```

## 16. Suggested implementation phases

### Phase 1: state separation

Introduce explicit separate state for:

* visible posted variations
* selected posted variation
* active draft
* focus position

### Phase 2: composed tree builder

Refactor tree rendering to build from base + visible posted + draft, rather than mutating one tree progressively.

### Phase 3: variation list controls

Add clear recall/select vs toggle behavior.

### Phase 4: visual identity

Add color-linked or equivalent identity from list item to branch.

### Phase 5: posting and live-update hardening

Ensure:

* posted creates immutable new entry
* new entry toggles on for poster
* live moves update base without focus snapping

## 17. Pitfalls to avoid

Do not:

* treat posted variation as editable after recall
* merge every recalled variation permanently into one ever-growing tree
* auto-hide other visible variations on recall
* snap user back to the live branch when new moves arrive
* let selection point at a hidden variation
* compose variations from different base games together
* make draft styling indistinguishable from posted history

## 18. Acceptance criteria

This implementation is correct if:

* a posted variation can be recalled and inspected without becoming editable
* multiple posted variations can be shown at once through explicit toggles
* recalling one leaves the others visible and only changes selection
* starting from a posted variation creates a new draft rather than modifying history
* live base-game updates continue while the user stays focused where they were
* tree branches remain understandable because visible posted variations have clear identity
* old-game variations do not pollute the current-game tree after a room board switch

## 19. Short version for the implementing agent

Build a **Kibitz-specific composed variation tree**.

Not generic shared tree behavior.

The tree is:

* base game branch
* plus any locally toggled-on immutable posted variations for that same game
* plus one optional editable draft branch

Recall:

* toggles target on if needed
* selects it
* focuses it
* leaves others on

Live updates:

* update base data
* do not move viewport

Editing:

* posted history is never edited
* editing from posted history creates a new draft
