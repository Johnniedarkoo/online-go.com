# Kibitz Variation Tree V2 spec

This spec defines the Kibitz-specific variation-tree model for posted variations. It replaces the simpler “show only one posted variation at a time” model with a richer but still controlled system: multiple posted variations may be shown together, but only through explicit user toggles. This is a deliberate product choice and justifies a custom implementation rather than relying on generic shared tree behavior.

## 1. Product goal

Kibitz variations should support social discussion without making the tree unreadable.

The design must satisfy all of these at once:

* posted variations are stable references people can discuss
* users can revisit old posted variations
* users can start new work from an old posted variation
* the live game branch remains current
* the tree does not silently fill up with uncontrolled clutter
* users can intentionally compare more than one posted variation when useful

The system therefore needs stronger rules than a generic move-tree viewer.

## 2. Core product decision

Kibitz uses three conceptual layers in the tree:

* **Base game layer**
* **Posted variation layer**
* **Draft variation layer**

These layers behave differently.

### Base game layer

The original game branch.

### Posted variation layer

Immutable posted variations that may be toggled visible or hidden.

### Draft variation layer

The user’s current unposted working branch.

This layered model is the core of the feature.

## 3. Fundamental rules

### Rule 1: posted variations are immutable

Once a variation has been posted to the room, its move content does not change.

Users may inspect it, toggle it, and start a new draft from it, but they do not edit it in place.

### Rule 2: draft variations are editable

A draft is the user’s current local working variation before posting.

It may change freely until posted.

### Rule 3: the base game remains authoritative

The original game branch is always the anchor of the tree.

If the source game is live, the base game branch should continue to receive new real moves.

### Rule 4: posted variations never auto-accumulate forever

The tree must not keep growing merely because the user clicked several variation recalls over time.

Visibility of posted variations must be explicit and controllable.

### Rule 5: visible posted variations must be clearly identifiable

If more than one posted variation is visible, users must be able to tell which branch belongs to which variation.

## 4. Tree composition model

At any moment, the displayed tree is composed from:

* the base game branch
* zero or more toggled-on posted variations that belong to that same base game
* optionally one active draft variation

This means the displayed tree is not a raw persisted tree. It is a composed view.

## 5. Base game behavior

### Purpose

The base game is the social reference point for the room.

### Requirements

* always available in the tree
* remains visually neutral and primary
* continues to extend if the source game is live
* serves as the attachment point for posted and draft variations

### Live game update rule

If the watched game is live and new real moves arrive:

* the base branch updates
* toggled posted variations remain intact
* draft variation behavior follows the draft rules below

The live branch must not become stale while viewing posted variations.

## 6. Posted variation behavior

### Definition

A posted variation is a persisted room variation that users can revisit and discuss.

### Requirements

* immutable
* recallable
* toggleable on/off in the tree
* visually identifiable
* selectable/focusable independently of visibility

### Visibility model

Each posted variation has a local UI visibility state for the current viewer:

* hidden
* visible

This state is not room-global.

One user may choose to view several posted variations while another chooses to view none.

### Default visibility

The safe default is:

* posted variations are off by default
* except the one the user has just recalled or just posted, which should turn on automatically

This prevents clutter while keeping the interaction intuitive.

## 7. Draft variation behavior

### Definition

A draft variation is the current editable working branch of the local user.

### Requirements

* editable
* not yet part of room history until posted
* visually distinct from posted variations
* may begin from the base game or from an existing posted variation

### Posting rule

When the user posts the draft:

* a new immutable posted variation is created
* the new posted variation becomes visible for that user automatically
* it receives its posted visual identity
* the draft state ends or resets appropriately

### Important distinction

Posting does not “convert a branch in place” in the user’s mental model. It creates a posted artifact from the draft.

## 8. Starting a new variation from an old posted variation

This is allowed.

### Behavior

If a user loads or focuses a posted variation, steps back, and begins playing moves:

* they are not modifying the posted variation
* they are creating a new draft variation derived from that posted variation’s position

### Product meaning

The posted variation remains stable.
The new line is a separate draft and may later be posted as a separate variation.

This is critical for discussion clarity.

## 9. Recall behavior

Clicking a variation recall control should do two things:

* focus that variation
* ensure it is visible in the tree

### Expected result

If the recalled variation is currently hidden:

* it becomes visible
* the tree focuses or jumps to its relevant branch or endpoint

If it is already visible:

* the tree still focuses it

Recall should therefore be a combined show-and-focus action, not just a passive selection.

## 10. Toggle behavior

Each posted variation in the variation list should have an explicit visibility toggle.

### Toggle on

When toggled on:

* the variation appears in the composed tree
* its visual identity appears in both list and tree
* it becomes available for focus/selection

### Toggle off

When toggled off:

* the variation disappears from the composed tree
* any list identity remains, but tree identity is removed

### If the toggled-off variation is currently selected

Recommended behavior:

* clear selection from that variation
* move focus back to the base game or leave current move position stable if still valid

The main rule is that selection state should never point to something invisible.

## 11. Selection and focus

The UI must clearly distinguish:

* visible
* selected
* active draft

These are not the same thing.

### Visible

A posted variation is included in the composed tree.

### Selected

A specific posted variation is the current focused variation.

### Active draft

The user is currently editing an unposted branch.

### Requirement

If multiple posted variations are visible, the selected one must be obvious.

Without that, the tree becomes hard to read.

## 12. Visual identity

Because multiple posted variations may coexist, visual identification is required.

### Minimum requirement

Each visible posted variation must have a consistent identity linking:

* the variation list item
* the tree branch

### Acceptable methods

* color linking
* labels
* both

### Recommended V2 direction

Use a color-linked model with optional labels.

For example:

* each visible posted variation gets a distinct accent color
* its recall/toggle marker in the list uses that color
* its branch in the tree uses that color
* selection uses an additional stronger highlight state

### Draft styling

The draft branch should remain visually distinct from posted ones, ideally neutral or subdued rather than sharing posted colors.

## 13. Color allocation rules

If color is used, it needs stable rules.

### Requirements

* colors are assigned per currently visible posted variation
* they should remain stable while visible
* they should not shuffle unnecessarily during minor interactions

### Practical rule

A variation should keep its assigned display color while toggled on.
If toggled off and later on again, reusing the same color is ideal when practical but not required for V2.

### Overflow rule

If more visible variations exist than comfortably supported distinct colors:

* either reuse colors with labels added
* or cap recommended simultaneous visible variations in the UI

The product should discourage extreme clutter rather than optimize for it.

## 14. Tree cleanliness rules

The system should actively resist clutter.

### Soft rule

Most users should normally view:

* base only
* or base plus one posted variation
* or base plus one posted variation plus one draft

### Advanced use

Viewing multiple posted variations is an advanced comparison feature, not the default steady state.

### UX implication

The UI should make one or two visible variations easy, and five or six feel possible but not encouraged.

## 15. Room/game compatibility rule

Multiple posted variations may only be composed into the same tree if they belong to the same base game.

If the room changes board:

* posted variations from the previous game must not be merged into the current game’s tree
* they should remain accessible as historical room items, but separate from the current game tree

This is essential.

## 16. Board change interaction

When the room changes to another watched game:

* the base game layer switches to the new game
* visible posted variations for the old game are cleared from the current tree view
* old variations remain available in room history under the previous game context
* new posted variations for the new game start from a clean visibility state

This avoids cross-game contamination.

## 17. Live game interaction

If the base game is live and receives new moves while posted variations are visible:

* the base branch should continue growing
* visible posted branches remain attached to their original branching points
* the tree should not lose toggle state
* the UI should not silently deselect visible posted variations

### Draft caution

If the user is editing a draft while live moves arrive, the implementation must decide how to preserve the draft cleanly. For V2, the safe rule is:

* preserve the draft as-is
* continue updating the base branch independently
* do not force-merge draft state into live state

## 18. Variation list behavior

The variation list becomes the control surface for posted branches.

Each list item should support at least:

* recall/focus
* toggle visibility
* visible/hidden indication
* selected indication

Optional:

* color indicator
* author
* move count
* created time

### Recommended interaction split

* clicking the title/body recalls and focuses
* clicking the toggle controls visibility

That keeps actions understandable.

## 19. Tree interaction behavior

Clicking within the tree should preserve the difference between viewing and editing.

### Posted branch clicks

Clicking moves within a posted branch should:

* navigate/view that branch
* not enter edit mode automatically

### Draft entry

To start a new draft from a posted variation, the user must perform a deliberate variation-start action, or begin play from that position in a way that the UI clearly treats as creating a new draft.

The system must not make it ambiguous whether the user is editing history.

## 20. Posting flow

When a user posts a draft variation:

1. the draft is validated
2. a new posted variation record is created
3. the variation is added to the room variation list
4. the new variation is automatically toggled on for the posting user
5. it receives posted visual identity
6. it becomes the selected/focused posted variation
7. other users can choose whether to toggle it on

This keeps the poster oriented while preserving viewer control for others.

## 21. Other-user behavior

When another user posts a variation:

* it appears in the room’s variation list / stream
* it does not have to appear in the local tree automatically
* it should be easy to recall or toggle on manually

This prevents noisy unsolicited tree changes.

### Optional enhancement

A subtle “new variation” indicator in the list is useful, but auto-showing it in the tree should be avoided by default.

## 22. Persistence model

The system should persist the variation data itself, but not necessarily each viewer’s toggle state.

### Persisted

* posted variation content
* metadata
* association to base game / room

### Local UI state

* which posted variations are currently toggled visible
* which one is selected
* current draft state

These should be treated as viewer-local session state unless there is a strong product reason otherwise.

## 23. Implementation model

The clean implementation approach is to treat the visible tree as a composed projection, not a permanently mutated canonical structure.

### Suggested high-level data model

* `baseGameTree`
* `postedVariations[]`
* `visiblePostedVariationIds[]`
* `selectedPostedVariationId`
* `activeDraftVariation`

### Suggested composition flow

1. load/render base game tree
2. overlay toggled-on posted variations for same base game
3. overlay active draft if present
4. apply selection/focus styling

This is much safer than letting recall clicks permanently mutate the tree structure.

## 24. Hard constraints for implementation

These should be treated as non-negotiable:

* posted variations are never edited in place
* hidden variations are not shown in the tree
* selection cannot refer to an invisible variation
* cross-game variations are never merged into one tree
* recall makes a variation visible if needed
* newly posted variations become visible for the poster
* live base-game updates continue while viewing posted branches

## 25. Out of scope for V2

These are reasonable later ideas, but not required now:

* collaborative shared visibility state
* per-variation inline labels rendered directly on every tree node
* advanced branch filtering
* pinning a fixed comparison set across sessions
* automatic semantic grouping of related variations

The point of V2 is controlled multi-visibility, not maximal tree intelligence.

## 26. Acceptance criteria

V2 succeeds if:

* users can revisit posted variations without fear that those lines changed
* users can intentionally show multiple posted variations together
* the tree stays understandable because visible branches are identifiable
* users can start a new draft from a posted variation without mutating it
* the base game remains current for live games
* viewing several posted variations is possible without silent uncontrolled clutter
* old-game variations do not pollute the current game tree after a board switch

## 27. Final summary

Kibitz Variation Tree V2 uses a custom layered model:

* the **base game** is always the anchor
* **posted variations** are immutable and explicitly toggleable
* **draft variations** are editable and separate from posted history

The displayed tree is a composed view of:

* the base game
* any user-selected posted variations for that same game
* the current draft, if one exists

Recalling a variation shows and focuses it. Posting a draft creates a new immutable variation and turns it on for the poster. Starting from an old posted variation creates a new draft rather than modifying history. The result is a tree that can support richer comparison while staying socially legible.

## 28. Suggested defaults where the discussion left room

These are the defaults I would implement unless the devs want otherwise:

* posted variations default to hidden
* recalling a variation toggles it on and selects it
* posting a variation toggles it on for the poster only
* other users do not auto-see new variations in the tree
* clicking a visible posted variation in the tree is view-only
* explicit user action is required to begin a new draft from a posted variation
* selection clears automatically if its variation is toggled off

There are two narrow questions still worth settling before coding if you want absolute clarity:

1. Should a variation recall also auto-toggle **off** the other currently visible posted variations, or should it leave them on and only change selection?
2. When a live base game receives new moves while the user is focused deep inside a posted variation, should the viewport stay where the user is, or gently snap back only if they were on the live branch?
