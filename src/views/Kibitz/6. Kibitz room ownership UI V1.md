# Kibitz room ownership UI V1.5 spec

## 1. Product goal

Introduce a real ownership model without making the room page heavier.

The UI should support:

* **Owner**

  * change room name
  * change room description
  * change live game
  * later: appoint/unappoint curators

* **Curator**

  * change room description
  * change live game
  * cannot change room name
  * cannot appoint others

But the room page should remain visually clean and board-first.

## 2. Core design decision

Ownership UI is **not** a new visible section.

Instead:

* the existing room title strip gets a **gear** affordance
* the gear opens a **popover**
* the popover is the entry point for ownership actions
* `Change board` disappears from the always-visible UI

This keeps governance accessible without permanently consuming space.

## 3. Main room UI changes

### Keep

The existing room stage identity strip remains the main visible anchor:

* room title
* current game subtitle
* player row

### Remove

Remove standalone governance actions from normal board UI:

* remove always-visible **Change board** from the stage
* remove always-visible **Change board** from the room list action row

### Add

Add a small **gear button** in the room title row, visible only for users with room-management rights.

That means:

* Owner sees gear
* Curator sees gear
* regular viewer does not

### Description visibility

The room description should remain **hidden by default** on the main room page.

It should not become a second subtitle line or a new block.

That preserves the cleaned-up page.

## 4. Gear popover model

The gear opens an anchored popover from the room title area.

This popover is the ownership/governance surface.

### V1 popover contents

For **Owner**:

* **Edit room details**
* **Change live game**

For **Curator**:

* **Edit room details**
* **Change live game**

But the contents of **Edit room details** differ by role.

### Future expansion

The popover structure should already anticipate:

* **People** / **Manage curators**

That item does not need to ship in v1, but the information architecture should leave room for it.

So the long-term structure is:

* About room
* Live game
* People

In v1, only the first two are active.

## 5. Edit room details behavior

### Open state

Choosing **Edit room details** keeps the user in the same popover flow.

This should not open a second modal.

### Owner fields

Owner can edit:

* room name
* room description

### Curator fields

Curator can edit:

* room description

Curator sees room name as read-only, or not editable at all.

### Save model

Use a compact form with:

* inline fields
* Save / Cancel
* no separate confirmation popup

This makes room editing feel light rather than administrative.

## 6. Change live game behavior

### Entry point

**Change live game** is launched from the gear popover.

### Surface

This action still opens the larger game-picker surface, because game selection is too big for a popover.

That gives a clean division:

* small room metadata edits stay in popover
* large board-picking flow uses overlay

### Permissions

* Owner: allowed
* Curator: allowed
* Viewer: unavailable

## 7. Create room flow redesign

The current desktop create-room flow should be simplified.

### Current problem

The flow is split across:

* game selection
* then a second popup for room name/description

That is unnecessary friction.

### New desktop create-room model

Keep the large overlay, but remove the separate details popup entirely.

Use:

* **left pane** = game source and selection
* **right pane** = selected game summary + room fields

### Right pane contents for create-room

* selected game metadata
* existing room suggestion
* room name field
* room description field
* Create room button

No second popup.

### Benefit

This fixes the specific complaint that room description entry is hidden in a popup despite desktop having enough space.

## 8. Change live game overlay redesign

The same game-picker core can still be reused, but its framing changes.

### Create room

Right pane contains:

* selected game summary
* room fields

### Change live game

Right pane contains:

* selected game summary
* confirmation/action area

No room fields.

That keeps the flows related but no longer identical.

## 9. Duplicate goban rule

This should be fixed with one clear rule.

### If source is Observe / ongoing list

Do **not** render a second goban in the right pane.

Reason:
the Observe list already provides the visual board preview.

So the right pane becomes:

* metadata
* actions
* room fields or confirmation

### If source is Game ID / URL

Do render the right-pane goban preview.

Reason:
there is no list-side board preview in this source mode.

This is the cleanest solution and directly fixes the wasteful “same goban twice” problem.

## 10. Ownership and visibility in the people UI

You chose the right place for public manager visibility:

**pin it to the top of the presence list.**

That avoids creating another new surface.

### Presence panel structure

At the top of the existing presence list:

* Owner row
* later: Curator rows
* then normal room roster

### Important detail

Managers should be visible there even if they are not currently active chat participants.

So this becomes a pinned management subsection inside the existing presence surface, not just “who happened to join most recently.”

### Visual treatment

Keep it subtle:

* owner icon/crown/star
* curator icon later
* small role label
* then ordinary users below

No new outer box needed.

## 11. Role model in UI

### Owner

Publicly visible as:

* pinned at top of presence list

Authorized controls:

* gear button visible
* can edit room name
* can edit description
* can change live game
* later can manage curators

### Curator

Not in v1 yet, but design assumes:

* also pinned near top of presence list
* gear button visible
* can edit description
* can change live game
* cannot edit room name
* cannot manage people

### Viewer

* no gear
* no governance actions
* still sees public manager identities in presence list

## 12. Why this is better than a “room block”

This respects the board-led layout:

* no new persistent vertical block
* no extra always-on row beyond a small gear
* no added clunky surface fighting for space with the goban
* governance moves out of the main action row
* create-room friction is reduced
* room roles become real without clutter

It also separates **activity** from **governance**:

* activity action: Create variation
* governance action: room gear

That is a much healthier product distinction.

## 13. Concrete component-level changes

### `KibitzRoomStage.tsx`

* remove the visible `Change board` button from `board-meta-actions`
* add a small gear button in the room title row
* gear opens ownership popover
* keep variation creation as the direct visible activity action

### `KibitzRoomList.tsx`

* remove the global/left-rail `Change board` action
* keep `Create room`
* keep `Create variation` only if still desired there

### `KibitzGamePickerOverlay.tsx`

* remove `showRoomDetailsPopup`
* inline room name + description fields on desktop create-room right pane
* keep change-live-game mode as confirmation-oriented
* when `sourceMode === "ongoing"`, suppress duplicate right-pane goban
* when `sourceMode === "game-id"`, keep right-pane goban

### `KibitzPresence.tsx`

* add pinned manager rows at top
* owner first
* future curator rows after owner
* then general roster

## 14. Acceptance criteria

This redesign succeeds if:

* room governance no longer adds a new always-visible section
* the room page stays as visually clean as it is now
* `Change board` is no longer treated like an ordinary board action
* create-room no longer needs a second details popup
* desktop Observe-based selection no longer shows the same goban twice
* owner visibility is public without adding another block
* the UI cleanly anticipates curator support later

## 15. Final summary

The right direction is:

* **gear in the existing room title strip**
* **popover for governance**
* **no visible Change board button**
* **no new ownership block**
* **create-room details inline in the desktop overlay**
* **no duplicate preview goban when Observe already shows one**
* **owner pinned to the top of the presence list**
* **future curators slot into the same presence + popover model**

That gives you a room-ownership model that feels real without undoing the layout cleanup.
